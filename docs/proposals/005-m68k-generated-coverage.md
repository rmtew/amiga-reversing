## Why This Exists

This project wants M68K tooling to be generated from the PRM-derived knowledge
base, not patched from memory. Coverage is the guardrail that tells us whether
the generated facts are good enough to support assembler, disassembler, and
eventually executor behavior.

The current codebase already does a lot:

- `knowledge/m68k_instructions.json` is generated by `src/scripts/kb/m68k_parser.py`.
- `src/generated/m68k_asm_tables.*` contains generated assembler form metadata.
- `src/generated/m68k_disassembler_tables.h` contains generated decode/disasm
  form metadata.
- `src/scripts/generate_c99_assembler_corpus.py` generates large assembler
  corpus files under `src/tests/generated/`.
- Several formerly "remaining" special forms now have generated corpus coverage,
  including `MOVEC`, `MOVES`, `CAS/CAS2`, bitfields, `RTD`, `STOP`, `TRAPcc`,
  and long multiply/divide forms.

The next problem is no longer just "add more instruction families". The next
problem is making coverage state explicit, shared, and hard to accidentally
weaken.

## Mental Model

Think of the pipeline as a contract chain:

```text
PRM PDF
  -> parser assertions and extracted tables
  -> knowledge/m68k_instructions.json
  -> canonical generated form inventory
  -> per-tool generated metadata
  -> samples, oracle checks, and coverage reports
```

The coverage question is not "did we generate many test cases?" It is:

```text
For every canonical generated form:
  Do we know whether it is sampleable?
  Do we know whether the assembler accepts it?
  Do we know whether the decoder/disassembler emits it?
  Do we know whether an external oracle accepts it?
  If not, is the unsupported status explicit and still current?
```

That makes coverage a metadata quality check. The corpus is only one consumer of
that metadata.

## Current State Read

The current implementation has useful generated tables:

```c
/* src/generated/m68k_asm_tables.h */
M68K_ASM_FORM_COUNT = 300
```

```c
/* src/generated/m68k_disassembler_metadata.h */
#define M68K_DISASM_FORM_COUNT 313u
```

That divergence is expected for now, but it is also the main smell. The
assembler and disassembler have related form inventories, but coverage does not
yet reason over one shared canonical universe.

Assembler corpus generation currently loops over generated forms and builds
sample combinations:

```python
for form in forms:
    ...
    options = _sample_options(context, item, kb, forms, subset_module)
    if any(not choice for choice in options) and "reglist" not in context.operand_kinds:
        continue
```

That `continue` is the important line conceptually. It is honest as a generator
implementation, but it means skipped forms are not automatically visible as a
coverage contract failure. A missing sample strategy and an intentionally
unsupported form can look the same.

The codebase has moved ahead of older coverage notes. Generated corpus files
already include many special forms:

```text
68020 corpus examples:
  MOVEC      present
  MOVES      present
  CAS/CAS2   present
  bitfields  present
  RTD/STOP   present
  TRAPcc     present
  long mul/div register-pair forms present
```

Remaining weak or absent areas should be reported explicitly. `MOVE16`,
`FSAVE/FRESTORE`, wider PMMU coverage, and generic coprocessor families are
best treated as intentionally unsupported inventory until the canonical model
and oracle story make them worth implementing. Decode/disasm parity gaps are
different: if the generated pieces already exist, the rewrite should connect
them cleanly rather than file them as future family work.

## Integration Findings

The assembler, disassembler, and simulator already moved away from the first
naive string-matching shape. That was the right correction: parse text at the
edge, convert to ids, and run the hot path over generated tables.

But the current integration still shows the scar tissue of incremental patches.
Those are useful signals for the rewrite.

### 1. Form Identity Is Still Split

Assembler metadata uses `g_m68k_asm_forms`.

Disassembler metadata emits its own `g_m68k_disasm_forms`, also shaped as
`M68kAsmFormDef`, then maps back to assembler forms through `asm_form_index`.

Textual shape today:

```text
asm form table
  form 0..299

disasm form table
  form 0..312
  each row may point back to asm_form_index
```

The runtime join is visible in disassembly result construction:

```c
canonical_form = &g_m68k_asm_forms[form->asm_form_index];
result_form = canonical_form->mnemonic_id != M68K_ASM_MNEMONIC_NONE
  ? canonical_form
  : form;
```

That works, but it is not a clean model. The disassembler should not own a
parallel form identity and then repair it back to assembler identity.

Target shape:

```text
canonical form table
  form_id 1..N
  asm view
  decode view
  render view
  simulator view
```

### 2. Lookup Still Has Scan-Based Fallbacks

Assembler form resolution scans generated forms by mnemonic and operand shape:

```c
for (index = 0; index < m68k_asm_form_count(); ++index) {
  const M68kAsmFormDef *form = &g_m68k_asm_forms[index];
  if (form->operand_count != operand_count) continue;
  if (form->mnemonic_id != mnemonic_id) continue;
  ...
}
```

That is much better than string matching, but the generated data can do better.
The generator should emit mnemonic-to-form ranges or a direct resolver table, so
runtime code does not rediscover grouping every time.

Simulator metadata has the same smell:

```c
for (index = 0; index < sizeof(g_m68k_sim_form_lookup) / sizeof(g_m68k_sim_form_lookup[0]); ++index) {
  const M68kSimFormLookup *entry = &g_m68k_sim_form_lookup[index];
  if (entry->mnemonic_id != mnemonic_id) continue;
  ...
  if (entry->asm_form_index == instruction->asm_form_index)
    return &entry->metadata;
  ...
}
```

The simulator should be indexed by canonical form id. If an instruction reaches
simulation without a canonical form id, that should be a decode/parse failure,
not a simulator fallback search.

### 3. Generated Facts Are Reimplemented As C Switches

`m68k_ir_codec.c` still has hand-maintained mnemonic family helpers:

```c
mnemonic_id_is_branch_family(...)
mnemonic_id_is_dbcc_family(...)
mnemonic_id_is_scc_family(...)
mnemonic_id_is_trap_family(...)
mnemonic_id_requires_long_size_suffix(...)
```

These are id-based rather than string-based, but they are still downstream M68K
knowledge. The parser already knows condition-code families, form syntax, size
rules, and semantic family. The generated model should expose those facts as
form or mnemonic metadata:

```json
{
  "mnemonic_id": "BNE",
  "condition_family": "bcc",
  "default_size_rule": "branch_displacement",
  "canonical_family": "conditional_branch"
}
```

Then IR codec code asks the table instead of carrying switch lists.

### 4. Sentinel And Index Conventions Are Mixed

Some ids use `0` as `NONE`. Some form arrays use valid index `0` and use
`FORM_NONE = FORM_COUNT`. Some operand indexes use `0xFF`.

All of those can work, but the mixture makes it easy to accidentally write the
old bug again: treating a selected array index as a nullable id.

The rewrite should split concepts:

```text
canonical_form_id:
  0 = none
  1..N = stable generated form ids

array_index:
  0..N-1 = storage offset
  never used as nullable identity

operand_index:
  0..3 = operand slot
  0xFF = no operand slot
```

This is the simple common-sense rule the earlier patch was reaching for: nullable
selection ids and dense array indexes are different types.

### 5. Disassembler Bucketing Is Good, But Tie Handling Belongs Upstream

The disassembler already uses generated buckets by opcode prefix, which is the
right direction:

```text
opword >> 4 -> candidate form indexes
```

Runtime still computes a specificity score and chooses the best match. That is
acceptable, but the generator has all the facts needed to pre-sort candidates
and fail on ambiguous equal-specificity forms.

Target behavior:

```text
generator sorts decode candidates by specificity
generator reports ambiguous ties
runtime returns first valid candidate
```

This keeps ambiguity checks near generated metadata instead of burying them in
decode control flow.

## Tutorial: Coverage Manifest

The first tutorial piece is the manifest because it makes the rewrite measurable.
Start by separating three questions that are currently mixed together.

```text
Question 1: Can the KB describe the form?
Question 2: Can the tool implement the form?
Question 3: Can the test generator produce useful samples?
```

A form can be KB-described but not sampleable. It can be sampleable but not
implemented. It can be implemented but missing oracle coverage. Those are
different states and should be represented differently.

### Step 1: Generate A Form Coverage Manifest

Add a generated manifest that records every canonical form and its coverage
status.

Illustrative shape:

```json
{
  "form_id": "MOVEC:0",
  "mnemonic": "MOVEC",
  "cpu_min": "68010",
  "syntax": "MOVEC Rc,Rn",
  "operand_kinds": ["ctrl_reg", "rn"],
  "assembler": {
    "metadata": "generated",
    "sample_status": "sampleable",
    "implementation_status": "implemented"
  },
  "disassembler": {
    "metadata": "generated",
    "decode_status": "implemented"
  },
  "oracle": {
    "vasm": "covered"
  }
}
```

The important part is not the exact JSON. The important part is that every form
has exactly one visible status.

Allowed sample statuses:

```text
sampleable
implemented_unsupported
intentionally_unsupported
missing_sample_strategy
```

`missing_sample_strategy` should be a failing status unless the caller is asking
for a report only.

### Step 2: Replace Silent Skips With Manifest Entries

Current corpus generation can skip forms when sample options are empty. Keep the
mechanics, but record the reason.

Current shape:

```python
options = _sample_options(context, item, kb, forms, subset_module)
if any(not choice for choice in options) and "reglist" not in context.operand_kinds:
    continue
```

Better shape:

```python
options = _sample_options(context, item, kb, forms, subset_module)
if any(not choice for choice in options) and "reglist" not in context.operand_kinds:
    coverage.record_missing_sample_strategy(
        form_id=context.form.coverage_id,
        operand_kinds=context.operand_kinds,
    )
    continue
```

Then strict mode can fail:

```python
if coverage.has_unclassified_forms():
    raise SystemExit(coverage.render_failures())
```

In the rewrite sequence, this is the measurement step before replacing the
assembler and disassembler integration. It makes skipped forms visible before
the old paths are deleted.

### Step 3: Add A Report Mode

A report mode should be readable without opening test code.

Example text output:

```text
M68K generated form coverage

Assembler forms:
  total:                  300
  sampleable:             276
  intentionally unsupported: 12
  implemented unsupported:   7
  missing sample strategy:   5

Missing sample strategy:
  MOVE16:0   operands=[absl, absl]
  FSAVE:0    operands=[ea]
  FRESTORE:0 operands=[ea]
```

Canonical command surface:

```powershell
uv run python -m amiga_reversing.tools.m68k_coverage report --phase diagnostic
uv run python -m amiga_reversing.tools.m68k_coverage check --phase diagnostic
uv run python -m amiga_reversing.tools.m68k_coverage report --phase canonical
uv run python -m amiga_reversing.tools.m68k_coverage check --phase canonical
```

`report` is human-readable and must not fail because coverage gaps exist.
`check` is strict and fails on unclassified forms, stale unsupported reasons,
asm/decode mismatches, missing sample plans, and equivalent coverage failures.

`diagnostic` reads the temporary bootstrap manifest. `canonical` reads the
canonical form model. Tests and PRD issue work should use this command surface;
unit tests may still exercise internals directly.

### Step 4: Make Unsupported Reasons Stale-Proof

Unsupported inventory should fail when it stops being true.

Illustrative inventory:

```json
{
  "form_id": "MOVE16:0",
  "status": "intentionally_unsupported",
  "reason": "requires MOVE16 paired absolute/register syntax sample plan",
  "expires_when": {
    "sample_status": "sampleable"
  }
}
```

Strict test behavior:

```text
If form is sampleable and still listed unsupported:
  fail with "stale unsupported reason"

If form is not sampleable and not listed unsupported:
  fail with "unclassified form"
```

This prevents static notes from becoming detached from code reality.

## Tutorial: Operand Sampling

Operand sampling is where downstream M68K knowledge currently tends to leak.
The clean direction is to make sample generation mechanical.

### Current Good Parts

The corpus generator already uses KB-derived effective-address metadata:

```python
def _ea_sample_options(...):
    ea_mode_sizes = _ea_mode_sizes(kb)
    allowed_ea_modes = ...
    ea_mode_order = tuple(
        name for name in _ea_mode_encoding(kb)
        if name in allowed_ea_modes
    )
```

That is the right direction. It means the sample set follows KB constraints.

### Current Friction

Special operands still need local knowledge in the corpus generator:

```text
ctrl_reg
cache_sel
rn_pair
dn_pair
bf_ea
PMMU function-code operands
coprocessor operands
```

Some of this is now properly sourced from parser assertions, but the corpus
generator still has too much responsibility for deciding what a valid operand
looks like.

### Generated Sample Plan

Generate operand sample plans from the KB or from parser-asserted KB entries.

Illustrative generated plan:

```json
{
  "operand_kind": "ctrl_reg",
  "samples": [
    {"text": "sfc", "value": 0},
    {"text": "dfc", "value": 1},
    {"text": "usp", "value": 2048}
  ]
}
```

For EA operands:

```json
{
  "operand_kind": "ea",
  "role": "src",
  "allowed_modes": ["dn", "ind", "postinc", "disp", "index", "absl"],
  "sample_families": ["register", "memory", "absolute", "indexed"]
}
```

Then corpus generation becomes an interpreter:

```python
for form in manifest.forms:
    sample_plan = manifest.sample_plan_for(form)
    if sample_plan.status != "sampleable":
        coverage.record(form, sample_plan.status)
        continue
    emit_cases(expand_samples(sample_plan))
```

This gives the manifest module depth: callers get useful classification and
sample plans from a small interface, while operand details stay local.

## Tutorial: EA Sampling Expansion

The current generated corpus is broad, but coverage should distinguish:

```text
one sample for a form
multiple representative EA samples for a form
all useful EA families for a form
```

For canonical `ea` forms, use generated EA mode tables to sample by family:

```text
register direct:
  d0

address register direct:
  a0

memory indirect:
  (a0)
  (a0)+
  -(a0)

displacement:
  $10(a0)

indexed:
  $10(a0,d1.w)
  full extension forms on 68020+

PC-relative:
  label(pc)
  label(pc,d1.w)

absolute:
  $1234.w
  $00123456.l

immediate:
  #$12
  #$1234
  #$12345678
```

The report should tell us whether a form is covered by only one EA sample or by
all required families.

Example status:

```json
{
  "form_id": "MOVE:ea,dn",
  "ea_coverage": {
    "src": {
      "required_families": ["register", "memory", "pc_relative", "absolute", "immediate"],
      "covered_families": ["register", "memory", "absolute"],
      "missing_families": ["pc_relative", "immediate"]
    }
  }
}
```

## Tutorial: Decode And Disassembly Parity

Assembler coverage and disassembler coverage should not grow separate mental
models.

Current textual picture:

```text
assembler generator      -> asm form table      -> assembler corpus
disassembler generator   -> disasm form table   -> decode tests
```

Better textual picture:

```text
canonical form manifest
  -> assembler metadata
  -> disassembler metadata
  -> simulator metadata
  -> corpus and coverage reports
```

The disassembler does not need to support every assembler alias. It does need to
map decoded instructions back to the canonical form universe.

Illustrative decode coverage entry:

```json
{
  "form_id": "TRAPcc:imm_word",
  "assembler": "sampleable",
  "decoder": "sampleable",
  "disassembler": "renders_canonical",
  "round_trip": "covered"
}
```

This lets tests ask stronger questions:

```text
Can assembler encode the form?
Can decoder recover the same canonical form id?
Can renderer print a syntax that assembler accepts again?
```

## Larger Architecture Observations

### 1. The Canonical Model Should Be A Deep Module

Right now, coverage knowledge is spread across:

```text
KB parser assertions
assembler table generator
corpus generator
generated test files
assembler parser/encoder
disassembler metadata
proposal text
```

The deletion test says the generated canonical model would earn its place. If
deleted, every caller would need to rediscover form identity, form status,
sample plans, generated family metadata, and unsupported state.

Deep module interface:

```python
model.forms()
model.sample_plan(form_id, cpu)
model.status(form_id, tool="assembler")
model.report(strict=True)
```

Implementation can be complex. Callers should not be.

### 2. Corpus Generation Should Stop Owning Knowledge

Corpus generation should not decide what `MOVEC`, `CAS2`, PMMU, bitfield, or
coprocessor operands mean. It should expand generated sample plans into files.

Bad long-term shape:

```text
corpus generator knows every weird operand family
```

Target shape:

```text
KB/parser knows operand families
canonical model exposes sample plans
corpus generator emits cases
```

### 3. Unsupported State Should Be Data

Unsupported state belongs in one inventory, preferably generated plus a small
declared overlay.

Textual illustration:

```text
generated facts:
  form exists
  operands are known
  CPU tier is known
  sample plan is absent

declared overlay:
  intentionally unsupported because external oracle cannot encode it yet
```

The overlay should be small and stale-proof.

### 4. Executor Coverage Is Related But Separate

Assembler/disassembler support proves syntax and encoding. Executor support
needs generated semantics.

Keep statuses separate:

```json
{
  "form_id": "RTE:none",
  "assembler": "implemented",
  "decoder": "implemented",
  "executor": "missing_generated_semantics"
}
```

Do not hardcode executor behavior downstream just to close coverage. If the
semantics are missing, fix parser/schema extraction first.

## Forward Implementation Model

The rewrite should not preserve the current assembler, disassembler, and
simulator integration shape. We are the only consumer, so the best implementation
is a simpler generated model with no compatibility layer and no legacy fallback
paths.

The core rule:

```text
one canonical generated form model
  -> parser/source syntax view
  -> assembler encode view
  -> decoder match view
  -> disassembler render view
  -> simulator/effect view
  -> sample/corpus view
  -> coverage view
```

The runtime tools should not rediscover relationships that the generator already
knows.

### Canonical Form Identity

The generated model should own instruction identity. Assembler, disassembler,
simulator, corpus generation, and coverage should all refer to the same form id.

Use separate types for nullable identity, dense storage, and operand slots:

```c
typedef uint16_t M68kFormId;      /* 0 = none */
typedef uint16_t M68kFormRow;     /* dense generated table row, never nullable */
typedef uint8_t M68kOperandSlot;  /* 0..3, 0xFF = none */
```

Canonical table shape:

```c
typedef struct {
    M68kFormId id;
    M68kMnemonicId mnemonic_id;
    M68kCpuLevel cpu_min;
    uint8_t operand_count;
    M68kOperandKind operands[4];
    M68kFormFlags flags;
    M68kSyntaxFamily syntax_family;
    M68kSemanticFamily semantic_family;
} M68kForm;
```

Rule:

```text
Runtime state carries M68kFormId.
Generated arrays use M68kFormRow internally.
Conversion between id and row is explicit.
```

This permanently avoids the old bug shape where `0` could mean both "no
selection" and "first generated row".

### Assembler Resolver

The assembler should parse text at the edge, convert to ids and operand kinds,
then use generated resolver tables.

Target flow:

```text
source text
  -> mnemonic_id
  -> parsed operands
  -> generated form resolver
  -> canonical form id
  -> generated encoder row
  -> bytes
```

The public internal operation can be simple:

```c
M68kFormId m68k_resolve_form(
    M68kMnemonicId mnemonic_id,
    M68kSize size,
    const M68kParsedOperand operands[4],
    uint8_t operand_count,
    M68kCpuLevel cpu
);
```

Its implementation should be generated data, not a scan over every form.

Generated lookup aids:

```text
mnemonic_id -> candidate canonical form id range
form_id -> operand matcher row
form_id -> accepted size rules
form_id -> alias/canonicalization rule
form_id -> encoder row
```

The assembler should not know special M68K families. `CAS2`, bitfields, control
registers, quick immediates, and coprocessor syntax should be generated operand
and syntax metadata.

### Decoder Candidate Model

The decoder should start from generated opcode buckets and produce a canonical
form id.

Target flow:

```text
opcode word
  -> generated decode bucket
  -> pre-sorted canonical form candidates
  -> generated field extractor
  -> canonical form id + decoded operands
```

Generated candidate shape:

```c
typedef struct {
    uint16_t opword_mask;
    uint16_t opword_value;
    M68kFormId form_id;
    uint16_t decoder_row;
} M68kDecodeCandidate;
```

Generator responsibilities:

```text
build decode buckets
sort candidates by specificity
fail generation on ambiguous equal-specificity matches
emit candidate form ids, not disassembler-private form ids
```

Runtime responsibility:

```text
try candidates in generated order
return the first valid decoded canonical form
```

Runtime decode should not score candidates or repair identities between
disassembler-specific and assembler-specific form tables.

### Disassembler Renderer

The renderer should consume decoded canonical form ids. It should not own a
parallel disassembler form identity.

Target flow:

```text
decoded canonical form id + decoded operands
  -> generated render row
  -> canonical or alias spelling
  -> source text
```

Generated render metadata should include:

```text
operand order
size suffix rule
condition-code spelling
alias preference
literal formatting class
control-register spelling
special operand render template
```

If the renderer needs to know that `DBRA` is an alias of `DBF`, that is generated
alias metadata, not a handwritten condition in render code.

### Simulator Semantics Lookup

The simulator should receive instructions that already carry canonical form ids.
It should not search by mnemonic and operand shape.

Target operation:

```c
const M68kSimSemantics *m68k_sim_semantics_for_form(M68kFormId form_id);
```

Target flow:

```text
decoded instruction with canonical form id
  -> form_id -> generated semantic/effect row
  -> execute or predict effects
```

If semantics do not exist:

```text
return generated_semantics_missing
```

Do not guess through fallback matching. Missing semantics means the parser/schema
does not yet express the required effect facts.

### Generated Family Metadata

Downstream C switches that classify mnemonic families should become generated
metadata lookups.

Replace helpers such as:

```c
mnemonic_id_is_branch_family(...)
mnemonic_id_is_dbcc_family(...)
mnemonic_id_is_scc_family(...)
mnemonic_id_is_trap_family(...)
mnemonic_id_requires_long_size_suffix(...)
```

with table access:

```c
M68kFormFlags flags = m68k_form_flags(form_id);
M68kSyntaxFamily syntax = m68k_form_syntax_family(form_id);
M68kSemanticFamily semantic = m68k_form_semantic_family(form_id);
```

Example generated families:

```text
conditional_branch
dbcc
scc
trapcc
quick_immediate
register_pair
bitfield
control_register
coprocessor
```

The parser/generator owns this classification. Runtime code consumes it.

### Sample Plans And Strict Coverage

Corpus generation should expand generated sample plans. It should not synthesize
M68K operand knowledge locally.

Sample-plan shape:

```json
{
  "form_id": 123,
  "sample_status": "sampleable",
  "operands": [
    {"kind": "ea", "families": ["dn", "indirect", "absolute"]},
    {"kind": "dn", "samples": ["d0"]}
  ]
}
```

Strict coverage should fail when:

```text
required form has no sample plan
assembler sample exists but decoder cannot recover the same form id
decoder can identify a form but no assembler spelling exists
unsupported reason is stale
semantic execution is enabled without generated semantics
```

These are rewrite closure failures, not optional report-only findings.

### Unsupported Family Inventory

Unsupported inventory is only for genuinely out-of-scope instruction families,
not for broken joins between generated pieces.

Initial intentionally unsupported families:

```text
MOVE16
FSAVE/FRESTORE
PMMU
generic coprocessor
```

Inventory entries should be structured:

```json
{
  "form_id": 271,
  "status": "intentionally_unsupported",
  "reason": "PMMU operand schema is not represented yet",
  "required_schema": [
    "pmmu_function_code",
    "pmmu_register",
    "pmmu_cache_mode"
  ]
}
```

That keeps future work clear: add the missing schema, regenerate the canonical
model, remove the unsupported entry, and let strict coverage prove the join.

## Generated Artifact Ownership

Ownership should follow the natural data flow. One generator decides what a form
is. Other generators emit tool-specific views of that form. Runtime files consume
those views.

Ownership split:

```text
KB parser / extractor
  owns raw instruction facts
  owns parser-asserted facts with citations
  owns knowledge/m68k_instructions.json

canonical model generator
  owns canonical form identity
  owns form ids and id-to-row mapping
  owns aliases
  owns operand roles
  owns syntax families
  owns semantic families
  owns generated form status inputs
  owns sample-plan and unsupported-status source data derived from the KB

assembler generator
  consumes canonical model
  emits mnemonic/form resolver tables
  emits operand matcher tables
  emits encoder tables

disassembler generator
  consumes canonical model
  emits decode buckets
  emits decode candidates
  emits field extractor tables
  emits render tables

simulator/effect generator
  consumes canonical model
  emits form_id -> semantic/effect metadata
  emits generated_semantics_missing status where semantics are absent

corpus/coverage generator
  consumes canonical model
  emits sample corpus
  emits coverage reports
  emits strict coverage failures
```

Expected generated artifacts:

```text
src/generated/m68k_forms.h
src/generated/m68k_forms.c
  canonical form ids, dense rows, common metadata, aliases, families, status

src/generated/m68k_asm_tables.h
src/generated/m68k_asm_tables.c
  assembler resolver, operand matcher, and encoder tables

src/generated/m68k_disassembler_tables.h
src/generated/m68k_disassembler_tables.c
  decode buckets, decode candidates, field extractors, and render tables

src/generated/m68k_simulator_tables.h
src/generated/m68k_simulator_tables.c
  form_id -> simulator/effect metadata

src/generated/m68k_sample_plans.json
  generated sample plans, unsupported inventory inputs, and coverage status
```

Consumer-only files:

```text
src/m68k_assembler.c
src/m68k_disassembler.c
src/m68k_simulator.c
src/m68k_ir_codec.c
src/scripts/generate_c99_assembler_corpus.py
tests
```

Consumer-only means these files may parse, execute generated table lookups,
format errors, and run tests. They should not decide what an M68K form is, which
family a mnemonic belongs to, how a special operand is sampled, or whether a
form is unsupported.

## Non-Goals

This rewrite is intentionally broad, but it should not silently grow into every
possible M68K implementation task. These non-goals keep the target sharp.

Non-goals:

```text
implementing MOVE16 now
implementing FSAVE/FRESTORE now
implementing PMMU now
implementing generic coprocessor families now
preserving old assembler/disassembler/simulator APIs for compatibility
preserving old generated table shapes for compatibility
making corpus generation a local home for missing ISA knowledge
hardcoding executor semantics downstream to close coverage
```

Unsupported instruction families can still be implemented later, but not as part
of this rewrite unless the canonical schema, generated sample plans, generated
decode/render metadata, and oracle story are ready enough to support them
cleanly.

No backward compatibility layer is required. Existing runtime and generated
interfaces should be replaced when replacement makes the model simpler, more
correct, and naturally efficient.

The corpus-generator non-goal is about ownership, not about blocking parser
improvements. Parser-asserted KB amendments are allowed and expected when the PDF
implies a fact that cannot be parsed directly. If sample generation needs a fact,
add it to the parser, schema, or canonical model, with the required citation and
explanation for parser assertions, then regenerate sample plans.

Bad ownership:

```python
if mnemonic == "MOVE16":
    invent_move16_samples()

if operand_kind == "pmmu_fc":
    guess_pmmu_function_code_syntax()
```

Good ownership:

```text
parser/schema or parser assertion
  -> knowledge/m68k_instructions.json
  -> canonical model
  -> generated sample plan
  -> corpus generator expands samples
```

Executor support follows the same rule. If an instruction needs semantics, the
semantics belong upstream in generated metadata. Downstream executor code should
consume generated facts or report `generated_semantics_missing`; it should not
encode M68K behavior from memory.

## Proposed Rewrite

Because this repository is the only consumer of the generated M68K tooling, the
best path is not a compatibility-preserving migration. The best path is a direct
rewrite to one canonical generated form model, with a short diagnostic slice at
the start so the rewrite is guided by current facts.

The rewrite should have one end state:

```text
knowledge/m68k_instructions.json
  -> generated canonical M68K form model
       -> assembler metadata
       -> disassembler metadata
       -> simulator/executor metadata
       -> sample plans
       -> coverage reports
       -> oracle corpus
```

There should be no long-lived compatibility shim, no duplicate old generator
path, and no second source of truth for form status.

### Slice 1: Diagnostic Manifest

First add a report-only manifest over the current generated forms.

Purpose:

```text
make current form inventory visible
make silent sample skips visible
make asm/disasm mismatches visible
make unsupported state explicit
```

This is not the new architecture. It is a bootstrap measuring tool with a short
lifetime.

Lifetime rule:

```text
The diagnostic manifest may exist only until the canonical model can produce the
same classification directly.

When the canonical model owns form identity, sample status, asm/disasm parity,
and unsupported inventory, the diagnostic manifest must be deleted or folded
into canonical-model reporting.

It must not remain as a parallel source of form identity, form status, sample
status, or unsupported inventory.
```

Exit conditions:

```text
canonical model lists every form
canonical model reports sample status
canonical model reports asm/disasm identity parity
canonical model owns unsupported inventory inputs
strict coverage consumes canonical model output
```

Example report:

```text
M68K generated form model diagnostic

assembler forms:     300
disassembler forms:  313
matched forms:       287
asm-only forms:       13
disasm-only forms:    26

sample status:
  sampleable:              276
  missing sample strategy:   5
  intentionally unsupported: 19
```

The key rule for this slice:

```text
Every generated form must be classified.
Unclassified forms fail strict mode.
```

### Slice 2: Canonical Form Model

Replace split assembler/disassembler form construction with one generated model
that owns canonical form identity.

Illustrative shape:

```json
{
  "canonical_form_id": "TRAPcc:imm_word",
  "mnemonic": "TRAPcc",
  "cpu_min": "68020",
  "syntax_family": "condition_code",
  "semantic_family": "trap_conditionally",
  "encoding": {
    "group": 0,
    "words": 2
  },
  "operands": [
    {"kind": "imm", "size": "w"}
  ],
  "tool_status": {
    "assembler": "required",
    "decoder": "required",
    "disassembler": "required",
    "executor": "semantic_metadata_required"
  }
}
```

The generated model should distinguish:

```text
canonical form
syntax alias
encoding variant
operand role
sample plan
tool capability status
oracle status
executor semantic status
```

Assembler and disassembler generators should consume this model. They should not
independently decide what a form is.

The model should emit separate typed handles:

```c
typedef uint16_t M68kFormId;      /* 0 = none, stable generated identity */
typedef uint16_t M68kFormRow;     /* dense array row, never nullable */
typedef uint8_t M68kOperandSlot;  /* 0..3, 0xFF = none */
```

Generated tables can still be dense arrays, but runtime state should carry the
nullable `M68kFormId`, not an array row pretending to be optional.

### Slice 3: Generated Sample Plans

Move sample strategy into the canonical model.

The corpus generator should stop knowing special M68K operand families. It
should expand generated sample plans.

Target shape:

```python
for form in model.forms_for_cpu(cpu):
    plan = model.sample_plan(form.id)
    if plan.status != "sampleable":
        coverage.record(form.id, plan.status)
        continue
    for case in expand_sample_plan(form, plan):
        emit_case(case)
```

Special operands become generated data:

```json
{
  "operand_kind": "rn_pair",
  "samples": [
    {"text": "(a0):(a1)", "regs": [0, 1], "address": [true, true]},
    {"text": "(d0):(a7)", "regs": [0, 7], "address": [false, true]}
  ]
}
```

EA sampling should also be generated by family:

```json
{
  "operand_kind": "ea",
  "required_families": ["register", "memory", "pc_relative", "absolute", "indexed"],
  "samples": [
    {"family": "register", "text": "d0"},
    {"family": "memory", "text": "(a0)"},
    {"family": "pc_relative", "text": "target(pc)"},
    {"family": "absolute", "text": "$00123456.l"},
    {"family": "indexed", "text": "$10(a0,d1.w)"}
  ]
}
```

### Slice 4: Replace Tool Generators

Once the canonical model exists, replace the old generator-local form logic.

Delete or fold these responsibilities:

```text
assembler-only form identity
disassembler-only form identity
corpus-side special operand guessing
local unsupported-form lists detached from generated status
tool-specific canonicalization that should be alias metadata
runtime form scans by mnemonic and operand shape
simulator fallback lookup by mnemonic and expected operand kind
IR-codec mnemonic family switch lists
runtime disassembler ambiguity scoring that the generator can decide
```

The assembler generator should emit parse/encode metadata from the canonical
model.

The disassembler generator should emit decode/render metadata from the same
canonical form ids.

The simulator generator should consume generated semantic status and refuse forms
whose semantics are not represented in the KB.

The generated model should provide direct lookup aids:

```text
mnemonic_id -> canonical form id range
canonical form id -> assembler encode row
canonical form id -> decode/render row
canonical form id -> simulator metadata row
decode bucket -> pre-sorted candidate canonical form ids
```

Runtime code should not reconstruct these relationships.

### Slice 5: Strict Coverage As Gate

After old paths are deleted, strict coverage becomes the gate.

Strict mode should fail when:

```text
a canonical form is unclassified
a required assembler form has no sample plan
a stale unsupported reason remains after a form becomes sampleable
assembler and decoder disagree on canonical form identity
an alias has no canonical target
executor support is added without generated semantics
```

Report mode should stay available for inspection:

```text
form coverage by CPU
form coverage by mnemonic
EA family coverage
alias coverage
oracle coverage
executor semantic coverage
unsupported inventory
asm/disasm parity
```

### Slice 6: Classify Unsupported Families

Only after the unified model is in place should remaining unsupported families
be reconsidered. Until then, unsupported state should be explicit data.

Initial intentionally unsupported family inventory:

```text
MOVE16                  needs canonical MOVE16 operand/sample plan
FSAVE/FRESTORE          needs generated FPU frame/save-restore facts
remaining PMMU forms    needs PMMU-specific schema coverage
generic coprocessor     needs coprocessor encoding/schema coverage
```

The other two cases are not family cleanup options and should not be deferred.
They are required rewrite closure conditions:

```text
decode works but sample plan is missing
  The decoder has enough generated data to identify the form, but corpus
  generation cannot yet produce a valid assembler spelling. The rewrite should
  add the missing sample-plan metadata or mark the whole family intentionally
  unsupported with a real reason.

assembler samples exist but decoder parity is missing
  The assembler can produce bytes, but the decoder/render path does not map
  those bytes back to the same canonical form. The rewrite should make the
  assembler and decoder share one canonical form id and fail strict coverage
  until they agree.
```

If any unsupported family is later promoted into implementation work, it should
follow the same rule:

```text
fix parser/schema first
regenerate canonical model
consume generated metadata downstream
delete old workaround
verify through strict coverage and oracle cases
```

## Acceptance Criteria

These criteria are a minimum bar for accepting the rewrite, not an exhaustive
definition of correctness. If implementation reveals another legacy path,
duplicate source of truth, generated-data mismatch, or unchecked unsupported
state, it must be handled even if it is not named here.

Required acceptance points:

```text
canonical form id is the shared identity across assembler, decoder,
disassembler, simulator/effect metadata, sample plans, and coverage

0 is reserved for "no form" in M68kFormId and is never treated as a valid dense
table row

dense generated table rows are represented separately from nullable form ids

assembler form resolution uses generated lookup tables or generated candidate
ranges, not a whole-form runtime scan

decoder candidates are generated as canonical form ids and ordered by generated
specificity

decode ambiguity is detected by the generator or strict coverage, not hidden in
runtime tie-breaking

disassembler rendering consumes canonical form ids and generated render metadata
instead of owning a separate form identity

simulator/effect lookup is by canonical form id, not mnemonic plus operand shape

missing simulator/effect semantics returns generated_semantics_missing rather
than falling back to guessed behavior

mnemonic family, size suffix, condition-code, alias, and render facts come from
generated metadata rather than handwritten downstream switch lists

sample generation expands generated sample plans instead of embedding special
M68K operand knowledge in corpus code

assembler sample -> decode recovers the same canonical form id for every
sampleable form

decode -> render -> assemble preserves bytes or canonical form identity where
round-trip rendering is expected

unsupported forms are explicit, stale-proof, and tied to missing schema,
missing generated semantics, or deliberately unsupported instruction families

strict coverage fails when assembler and decoder disagree on canonical form
identity

strict coverage fails when a generated form is required but has no sample plan
and no explicit unsupported reason
```

## Deletion Checklist

This checklist names known cleanup targets. It is not a license to keep other
legacy code merely because it is not listed. During implementation, any code path
that preserves the old split identity model, fallback matching, or downstream
M68K knowledge should be deleted, folded into the generator, or justified as a
temporary bootstrap tool with an explicit removal point.

Known deletion or fold-in targets:

```text
assembler-only form identity

disassembler-only form identity

runtime joins from disassembler-private forms back to assembler forms

runtime whole-form scans by mnemonic and operand shape

simulator fallback lookup by mnemonic and expected operand kind

IR-codec mnemonic family switch helpers

handwritten size suffix and condition-family switch lists

runtime disassembler specificity scoring when the generator can pre-sort and
reject ambiguous ties

corpus-side special operand guessing

local unsupported-form lists detached from generated status

tool-specific canonicalization that should be generated alias metadata

diagnostic manifest code once the canonical model can produce the same
classification directly

any diagnostic manifest data path that remains as a parallel source of form
identity, sample status, asm/disasm parity, or unsupported inventory after the
canonical model exists
```

## Rewrite Acceptance Tests

These tests are the concrete proof points for the rewrite. They are not the only
tests the implementation may need; they are the minimum tests that show the new
model is actually being used end to end.

Required rewrite tests:

```text
canonical form id uniqueness
  Every generated canonical form has a nonzero M68kFormId.
  Every M68kFormId maps to exactly one dense row.
  Dense row 0 is valid storage but is never confused with "no form".

assembler resolve -> encode
  Each sampleable source case resolves to a canonical form id.
  The encoder row is reached through that canonical form id.
  No assembler test path scans every generated form at runtime.

assembler -> decoder parity
  For each generated sample case, assembler bytes decode back to the same
  canonical form id.

decoder -> renderer -> assembler parity
  For each renderable decoded case, rendered source reassembles to the same
  bytes or the same canonical form identity, depending on the form's declared
  round-trip expectation.

decode ambiguity rejection
  Generated decode buckets contain candidates sorted by generated specificity.
  Equal-specificity ambiguous candidates fail generation or strict coverage.

simulator metadata lookup
  Simulator/effect metadata is found by canonical form id.
  Forms without generated semantics return generated_semantics_missing.
  No simulator test path falls back to mnemonic plus operand-shape lookup.

generated family metadata
  Branch, DBcc, Scc, TRAPcc, size-suffix, alias, and render-family behavior is
  driven by generated metadata.
  Handwritten downstream family switch lists are absent from the tested path.

sample-plan ownership
  Corpus generation expands generated sample plans.
  Special operand samples come from parser/schema/canonical-model facts, not
  corpus-local mnemonic rules.

unsupported inventory
  MOVE16, FSAVE/FRESTORE, PMMU, and generic coprocessor families are either
  explicitly unsupported with structured reasons or fully supported by generated
  schema, sample plans, decode/render metadata, and oracle coverage.
  Stale unsupported reasons fail strict coverage.

coverage closure
  A generated form with required assembler or decoder support cannot be
  unclassified.
  A required form cannot be missing both a sample plan and an unsupported reason.
  Assembler and decoder canonical form identity mismatches fail strict coverage.
```

### Follow-Up Findings

#### 1. Canonical Coverage Does Not Actually Check Real Canonical Id Parity

`m68k_coverage.build_canonical_inventory()` is still a relabeled diagnostic
inventory. `_form_identity()` does not include `canonical_form_id`, so current
strict coverage only checks canonical id mismatches in synthetic tests that
manually insert ids.

Impact:

```text
strict canonical coverage can pass even if generated asm/disasm canonical ids
diverge in real generated output
```

Required follow-up:

```text
coverage inventory must read or compute canonical_form_id for assembler and
disassembler forms, then fail strict mode on real id mismatches.
```

2026-05-17 implementation update: issue 027-001 addressed the immediate gate.
Canonical coverage now reads canonical ids from the generated assembler and
disassembler C artifacts, records those ids in inventory entries, fails strict
mode for required matched asm/disasm canonical id drift, and prints canonical
summaries on successful `check --phase canonical`.

Important implementation factors found during 027-001:

- Disassembler generated table row order is not the Python form index order.
  The checker must not join by slot. It currently joins disassembler artifact
  rows by encoding identity: mnemonic, syntax, CPU mask, opword base/mask, and
  bound-word base/mask.
- Syntax strings can contain braces, e.g. bitfield `{offset:width}`. Generated
  artifact parsing must locate the operand array before reading numeric fields;
  splitting on the first `}` corrupts bitfield rows.
- Some unsupported PMMU rows share the current coarse inventory identity while
  carrying distinct canonical ids. Strict canonical id parity therefore skips
  forms already classified under unsupported families. This is not a general
  exemption: once 027-003/027-004/027-005 remove the unsupported reason or
  replace the coarse identity with the canonical model, those rows must be
  required again.
- Artifact parsing in `m68k_coverage.py` is an interim validator. It is useful
  because it checks emitted data rather than only recomputing generator helper
  output, but the clean end state is still a generated canonical manifest/model
  owned upstream.

#### 2. Unsupported Stale Checks Are Mostly Placeholders

Unsupported inventory entries contain `stale_conditions`, but
`blocking_artifacts_still_missing` is always emitted with `stale: false`. The
only effective stale check is "does this unsupported family still match at
least one current generated form?"

Impact:

```text
strict coverage will not fail when MOVE16, FSAVE/FRESTORE, PMMU, or generic
coprocessor blockers are actually resolved but the unsupported entry remains
```

Required follow-up:

```text
compute each stale condition from current generated data:
  canonical sample plan present
  decode/render metadata present
  generated semantics present or explicitly missing
  oracle support present or explicitly unavailable
```

2026-05-17 implementation update: issue 027-002 replaced the placeholder stale
logic with computed active blockers. Unsupported families now stay classified
only while at least one configured blocker is active in current generated data.
Strict coverage fails if an unsupported entry has no active blockers.

Current active blockers:

```text
MOVE16:
  generated_semantics
  oracle_support

FSAVE/FRESTORE:
  oracle_support

PMMU:
  canonical_sample_plan
  decode_render_metadata
  oracle_support

generic coprocessor:
  canonical_schema
  decode_render_metadata
  oracle_support
```

Important implementation factors found during 027-002:

- `generated_semantics` is no longer treated as active for a family merely
  because the family was listed unsupported. Coverage reads simulator semantic
  status counts; FSAVE/FRESTORE currently have structural simulator metadata and
  are kept unsupported by oracle coverage, not by missing simulator rows.
- `oracle_support` is currently derived from sample coverage status. An
  `oracle_unavailable` sample or an unsampled family keeps the blocker active.
  When oracle ownership becomes more explicit, this should read that artifact
  directly instead of inferring from sample statuses.
- `decode_render_metadata` is active when a family has unmatched asm/disasm
  rows or missing canonical ids. It catches current PMMU and generic
  coprocessor disasm-only rows.
- `canonical_schema` remains an explicit blocker for generic coprocessor forms
  because no generated coprocessor-ID schema artifact exists yet.

#### 3. Simulator Semantic Coverage Is Contradictory

The canonical coverage summary hardcodes:

```text

```

But `src/generated/m68k_simulator_tables.h` emits 300
`M68K_SIM_SEMANTICS_AVAILABLE` rows. At the same time, unsupported inventory
marks MOVE16, FSAVE/FRESTORE, and PMMU as blocked on generated semantics.

Impact:

```text
coverage cannot currently distinguish "metadata row exists" from "semantics are
actually generated and trustworthy"
```

Required follow-up:

```text
simulator generator must emit real semantic statuses per canonical form:
  available
  generated_semantics_missing
  intentionally_unsupported

coverage must consume those statuses instead of hardcoding executor semantics
as unavailable or treating every simulator row as available.
```

2026-05-17 implementation update: issue 027-003 added generated simulator
semantic statuses and coverage now reports counts from
`src/generated/m68k_simulator_tables.h`. Current canonical coverage reports:

```text

Important implementation factors found during 027-003:

- `M68kSimFormMetadata` is structural metadata used by analysis as well as the
  concrete simulator. Marking every unimplemented concrete operation as
  `generated_semantics_missing` breaks analysis paths that still need decode,
  flow, operand, or CPU metadata. Semantic status must therefore mean "do not

- Unsupported inventory now records simulator semantic status counts per family,
  but stale evaluation is still issue 027-002. Do not treat a family as resolved
  just because structural simulator metadata exists.

```

A generator test now fails if that digest changes accidentally. The only
generated artifact change from 027-004 is the provenance comment in
`src/generated/m68k_form_model.h`, which now names
`src/scripts/m68k_canonical_model.py`.

#### 5. Canonical Model Data Lives In A Static Header

`m68k_form_model.h` defines large `static const` arrays directly in the header.
Every translation unit that includes it gets its own copy.

Impact:

```text
unnecessary object size growth
harder symbol inspection
inconsistent with the proposal's expected src/generated/m68k_forms.c ownership
```

Required follow-up:

```text
split declarations into m68k_forms.h and storage into m68k_forms.c.
```

2026-05-17 implementation update: issue 027-005 kept the existing public
artifact name `src/generated/m68k_form_model.h` and added
`src/generated/m68k_form_model.c`. The header now exposes only types,
constants, extern arrays, and lookup declarations. The C file owns
`g_m68k_canonical_forms`, `g_m68k_canonical_form_id_by_row`,
`g_m68k_canonical_form_row_by_id`, `m68k_form_id_for_row()`, and
`m68k_form_row_for_id()`.

The generated artifact names differ from the earlier illustrative
`m68k_forms.h` / `m68k_forms.c` wording to avoid gratuitous include churn while
still removing duplicate static header storage.

#### 6. Runtime Lookup Is Improved But Not Fully Indexed

Assembler resolution now uses generated mnemonic ranges instead of scanning all
forms, which is good. It still scans within each mnemonic range by operand
shape. Simulator metadata lookup scans `g_m68k_sim_form_lookup` linearly by
canonical id.

Impact:

```text
the old whole-table scans are mostly gone, but canonical form id is not yet the
direct index promised by the proposal
```

Required follow-up:

```text
emit direct lookup tables:
  canonical form id -> asm row
  canonical form id -> disasm/render row
  canonical form id -> simulator metadata row/status
  mnemonic id + operand shape -> candidate range or resolver row
```

2026-05-17 implementation update: issue 027-006 completed the direct lookup
slice. The existing generated assembler table already provides canonical form
id -> assembler row lookup. The disassembler generator now emits
`g_m68k_disasm_form_index_by_canonical_id`, exposed through
`m68k_disasm_form_index_for_canonical_id()`. The simulator generator now emits
both `g_m68k_sim_lookup_index_by_canonical_id` and
`g_m68k_sim_semantic_status_by_canonical_id`; valid canonical forms without a
simulator row report generated semantics missing rather than form-not-found.

The remaining assembler resolver scan is limited to the generated mnemonic
candidate range while matching operand shape. It is not a whole-form-table
fallback. Further replacement with mnemonic+operand-shape resolver rows is a
possible optimization, not a blocker for this proposal's direct canonical-id
lookup requirement.

#### 7. Some Downstream M68K Family Knowledge Remains

`m68k_ir_codec.c` no longer carries the old mnemonic-family helper switches, but
`platform_file_core.c` still has `mnemonic_id_is_branch_family()` for byte-sized
branch target recovery. The implementation pass also found a facts-v2 DBcc
range check and conditional branch/DBcc fallthrough-confidence check.

Impact:

```text
branch-family knowledge remains downstream from generated metadata
```

Required follow-up:

```text
replace this with generated mnemonic/form family metadata or simulator flow
metadata.
```

2026-05-17 implementation update: issue 027-008 replaced the
`platform_file_core.c` byte-sized branch family switch with generated mnemonic
family metadata. It also replaced the facts-v2 conditional branch/DBcc range
checks with generated simulator flow and operation metadata.

Residual follow-up from the same audit: other analysis/rendering paths still use
exact mnemonic ids or mnemonic ranges for control-flow classification, including
`m68k_decode_ir.c`, `m68k_symbolic_parse.c`,
`platform_amiga_bootloader_analysis.c`, `m68k_analysis_render_lookup.c`, and
`m68k_render_ir.c`. Some exact mnemonic checks may be domain-specific behavior,
but each remaining range or flow-family check needs either generated metadata or
an explicit local justification. Tracked by `docs/issues/027-010-remove-remaining-downstream-flow-family-knowledge.md`.

2026-05-17 implementation update: issue 027-010 removed the residual broad
flow/family classifiers from those paths. Decode target collection now derives
branch/call/jump target kind and target operand index from simulator flow
metadata. Symbolic parsing uses generated mnemonic family metadata for relative
label operands. Bootloader successor tracing, render state invalidation,
helper fallthrough, call clobbering, and direct control-target helpers now use
generated simulator flow metadata instead of local Bcc/DBcc/JSR/JMP/return
lists.

Exact mnemonic checks that remain after this pass are intentional recognizers
for local project idioms rather than replacement flow classifiers:

```text
DBF:
  bootblock runtime-copy loop detection requires the DBF counter-loop idiom,
  not any DBcc-family branch.

RTS:
  local wrapper and helper-output recognition requires a normal subroutine
  return boundary. RTE/RTR are not equivalent wrapper completions.

JMP:
  Amiga LVO wrapper recognition treats JMP through an LVO as a tail-call
  wrapper. That exact tail-call shape is distinct from generic jump flow.
```

#### 8. Sample Plans Are Still Partly Corpus-Owned

The corpus generator has a sample-plan surface, but it still owns special
operand sample construction for register pairs, cache selectors, bitfield EA,
absolute forms, and other operand details.

Impact:

```text
corpus generation is becoming an interpreter, but it still embeds M68K operand
knowledge that should move to parser/schema/canonical-model data
```

Required follow-up:

```text
promote operand sample registries and per-form sample plans into generated
canonical artifacts. The corpus generator should only expand those plans.
```

2026-05-17 implementation update: issue 027-007 added
`src/generated/m68k_corpus_sample_plans.json` as the generated corpus sample
plan artifact. The corpus generator now builds serializable
`GeneratedCorpusSamplePlanEntry` rows and consumes those rows back into runtime
sample objects before emitting cases. This makes case generation an expansion
step over generated sample-plan data instead of a direct walk over ad hoc
operand helper output.

The generated entries include `form_index` as part of their identity. That is
required because forms such as `LINK.W` and `LINK.L` can share KB mnemonic,
local form index, and syntax while differing in generated form row and opcode.

#### 9. Canonical Check Output Uses Diagnostic Formatting

`m68k_coverage check --phase canonical` prints the diagnostic report on success
instead of the canonical report. The `report --phase canonical` command includes
canonical summaries.

Impact:

```text
minor UX bug, but it hides canonical summaries in the successful strict command
that developers are most likely to run
```

Required follow-up:

```text
on successful canonical check, print the canonical report or a concise canonical
check summary.
```

### Follow-Up Issue Tracking

No separate PRDs are needed for this follow-up work. This proposal is the
durable spec. `docs/issues/027-*.md` contains the executable slices and should be
deleted when each slice is completed, abandoned, or superseded. Any new durable
reasoning discovered while implementing those issues should be promoted back
into this proposal before deleting the issue file.

Implementation posture:

```text
This repository is the only consumer of the generated M68K tooling. Prefer
clean replacement, deletion of old paths, and generated-data ownership over
compatibility shims, bolt-on validators, or downstream workarounds.
```

Minimum verification for any code-changing follow-up issue:

```text
focused test for the changed behavior
uv run python -m amiga_reversing.tools.m68k_coverage check --phase canonical
cmd /c src\precommit.bat
```

Strict gate rollout rule:

```text
New strict coverage failures should become mandatory in the same issue that
makes their required data available. If a check depends on a later issue, keep it
report-only and name the blocking issue in the report until the blocker lands.
```

Canonical coverage must not be self-validating:

```text
Coverage checks should compare generated artifacts or independently loaded
generated tables. They should not pass only because they recompute canonical ids
through the same helper path that generated the ids being checked.
```

Canonical id stability rule:

```text
Canonical ids are internal, but they flow through C structs, generated corpus
manifests, diagnostics, and tests. Accidental reorder must fail. Intentional id
changes require an explicit proposal note explaining why they are safe.
```
